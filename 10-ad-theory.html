Prerequisites — The Why

AD Is a Database

NTDS.dit is the actual AD database on every DC. Every attack — Kerberoasting, DCSync, ACL abuse — is ultimately reading or writing entries in that database via LDAP. Understanding objects and attributes is understanding what you're attacking.

The Four Properties That Explain Kerberos Attacks

Property 1 — KDC never validates authorization when issuing a TGS.
It checks the TGT is valid, then issues the ticket. Authorization happens at the service, not the KDC. This is why Kerberoasting works — any authenticated user can request a TGS for any SPN.
Property 2 — The KDC trusts the KRBTGT hash absolutely.
TGTs are encrypted with KRBTGT. The KDC can't tell if a TGT was legitimately issued or forged. Golden Tickets exploit this — forge a TGT with the KRBTGT hash and the KDC accepts it unconditionally.
Property 3 — Service tickets are encrypted with the service account's hash.
The KDC never sees inside the TGS it issues. Silver Tickets exploit this — forge a TGS with the service account hash and present it directly to the service. The KDC is never involved. Zero DC logs.
Property 4 — Pre-authentication is optional.
Normally AS-REQ includes a timestamp encrypted with the user's hash. If pre-auth is disabled, the KDC sends back the AS-REP blob without proof of identity. AS-REP Roasting exploits this.

NTLM & SMB — The Critical Distinction

Net-NTLMv2 ≠ NTLM hash. Net-NTLMv2 is the captured challenge-response. You can crack it offline or relay it — but you cannot Pass-the-Hash with it. NTLM hash = PtH directly. Most common confusion point in AD attacks.

SMB signing and what it actually blocks:

SituationWhat You Can Do
No creds, signing disabledRelay NTLM auth to SMB → direct execution
No creds, signing enabledCapture Net-NTLMv2 → crack offline, or relay to LDAP/HTTP/ADCS
Have NTLM hash, signing enabledPtH directly — signing doesn't block PtH
Have NTLM hash, signing disabledPtH, or relay coerced auth from that machine elsewhere

DCs have SMB signing required by default. Workstations do not. This gap is the relay target.

Module 1 — AD Fundamentals

⚡ Commands: AD Fundamentals → 05

Forest, Domains, Trusts

Domain = one NTDS.dit, one KDC, one administrative boundary. Forest = collection of domains sharing schema. Enterprise Admins live in the forest root.

Domain boundaries are not security boundaries in practice. Owning a child domain almost always means owning the forest root via SID history or trust ticket attacks.

Trusts are often transitive. Large orgs accumulate forgotten trusts through acquisitions. Old trusts to weakly-secured domains are real attack paths.

Object Types — What to Target

ObjectKey PropertyOffensive Relevance
UsersSPN set = KerberoastableTarget if adminCount=1 or DA member
ComputersAuthenticate as MACHINE$Machine account hash usable for lateral movement; SYSTEM = authenticates as machine
Service accountsPassword never expires, SPN set, often over-privilegedPrime Kerberoast targets; DA membership embarrassingly common

adminCount=1 = account touched a protected group at some point. BloodHound surfaces this automatically.

ACL Permissions — The Hidden Attack Surface

GPOs as Attack Surface

Write access to a GPO linked to a sensitive OU = code execution on every object in that OU at next refresh (default 90 min). Write access to a GPO linked to the Domain Controllers OU = instant domain compromise.

Module 2 — Enumeration

⚡ Commands: Enumeration → 05
bloodhoundldap sysvolspns

What Enumeration Actually Is

Reading the AD database as a legitimate domain user. No exploitation. No noise. Pure LDAP queries. Three questions: who exists, what's misconfigured, what's the path to DA.

The Five Layers

LayerWhat You're Looking ForWhy It Matters
1 — Domain StructureDomain name, DC IPs, functional level, trustsFunctional level = encryption support. Old = RC4 everywhere = faster cracking.
2 — Users & GroupsAll users + last logon, password last set, adminCount. Nested group membership.Old passwords = weak. Nested membership: user in GroupA in DA = DA.
3 — Attack SurfaceSPNs, pre-auth disabled, unconstrained delegation, LAPS readersDirect targeting list. Non-DC with unconstrained delegation = misconfiguration.
4 — ACL EnumerationDangerous rights on users, groups, GPOs, OUsMost underused layer. BloodHound surfaces hidden privilege chains.
5 — Shares & SYSVOLScripts, GPP XML, config files, credentialsAdmins treat internal shares as safe. They're not.

BloodHound — Why It Changed Everything

Models AD as a graph. Nodes = objects. Edges = relationships and permissions. Finds multi-hop privilege chains in seconds that would take hours manually.

When to rerun SharpHound: one collection per domain context. Not per privilege level. Not per new machine. Per domain. New domain or crossed a trust = rerun. Same domain low-priv = never rerun.

Enumeration Mindset

Enumeration is not a phase — it's continuous. Every new credential unlocks more LDAP access. Every new machine reveals new sessions. Loop back every time you move laterally.

Never move to exploitation without finishing enumeration first. The number of engagements where direct path to DA was visible in BloodHound from the first foothold and the attacker didn't look is embarrassingly high.

Why Each Attack Works

Kerberoasting: KDC issues TGS to any authenticated user (Property 1). The blob is encrypted with the service account's hash. Take it offline, crack it. No vulnerability exploited — protocol working as designed.

AS-REP Roasting: Pre-auth disabled (Property 4). KDC sends back the AS-REP without verifying identity first. The blob is partially encrypted with the user's hash. Crack offline — no credentials required, just a username.

NTLM Relay: You can't crack Net-NTLMv2 in real time, but you can forward it. Relay to a service that accepts NTLM and you authenticate as the victim. ESC8 is NTLM relay to ADCS HTTP enrollment. SMB relay is NTLM relay to file servers.

Password spray: Password complexity policies force predictable patterns. Winter2024! passes most policies but is guessable. One password across all users = low lockout risk, high yield.

Kerberoasting Priority Order

SPN + DA member → crack first, highest impact SPN + adminCount=1 → crack second SPN + password never expires → crack third (likely weak) SPN + regular user → crack last

What Determines Your Technique

Your credential material type dictates the technique — not preference.

Plaintext → everything NTLM hash → PtH (SMB, WMI, WinRM) Net-NTLMv2 → relay only TGT → PtT, request any TGS TGS → that specific service only Certificate → PKINIT → TGT → everything

Why Pass-the-Hash Works

NTLM authentication uses the hash directly as the cryptographic secret. The protocol never needs the plaintext — so neither do you. Local admin hash reuse: before LAPS, one cracked local admin hash = local admin on every machine in the domain.

Remote Execution: Noisiest → Quietest

MethodNoiseWhy

The Critical: Sessions Are Runtime State

BloodHound = static map (AD configuration). Live machine enumeration = dynamic state (who's here right now). A DA's TGT in LSASS on a machine you just compromised is pure opportunity — but only if you check. --loggedon-users on every new machine. Always.

Module 5 — Privilege Escalation

⚡ Commands: Privilege Escalation → 05
ACL abusedelegation GPORBCD

What You're Actually Doing

Finding the one misconfiguration that bridges your current access to DA. Almost entirely logic-based — protocol abuse, not memory corruption. The techniques are diverse; the pattern is always the same: find a permission someone set and forgot about.

ACL Abuse — The Prod-Safe Priority

Never reset a service account password without client approval in prod. Services break immediately. Down services = 2am calls.
If You Have GenericAllDo This FirstWhy
Account has existing SPNJust Kerberoast itZero modification, reversible, silent
No SPNShadow Credentials (pywhisker)No password change, service unaffected, cert-based auth
No SPN, shadow creds failsFake SPN + Kerberoast + remove SPNMinor modification, fully reversible
Account confirmed stalePassword resetNuclear option — confirm service dependency first

Why Unconstrained Delegation Is So Dangerous

When any user authenticates to a machine with unconstrained delegation, their TGT is automatically forwarded and stored in LSASS on that machine. Combine with a coercion primitive (PetitPotam, PrintSpooler) to force the DC's machine account to authenticate → capture its TGT → DCSync. Non-DC machine with unconstrained delegation = misconfiguration, always investigate.

Why RBCD Matters

Resource-Based Constrained Delegation converts write access to a computer object (a common misconfiguration BloodHound surfaces as GenericWrite or WriteProperty) into full compromise of that machine. Any domain user can create up to 10 machine accounts by default — no special privileges needed to set up the attack.

AdminSDHolder — Self-Healing Persistence

SDProp runs every 60 min and resets ACLs on all protected accounts to match the AdminSDHolder template. Write an ACE to AdminSDHolder = SDProp propagates it to every DA, EA, and protected account automatically. Survives your removal from DA. Survives most incident response actions. Nobody audits AdminSDHolder ACLs.

Module 6 — ADCS Attacks

⚡ Commands: ADCS Attacks → 05
ESC1ESC8 certipyPKINIT

Why ADCS Is Critical-by-Default

A certificate allowing authentication is functionally equivalent to a password that never expires and survives password resets. That's why ADCS findings are almost always Critical. Run certipy find -vulnerable on every engagement where ADCS is installed — one command, instant Critical findings.

ESC1 — Why It Works

Three conditions: CT_FLAG_ENROLLEE_SUPPLIES_SUBJECT flag set + low-priv enrollment rights + Client Authentication purpose. The CA issues the certificate with whatever SAN (Subject Alternative Name) you specify. When you authenticate via PKINIT, the KDC reads the SAN, sees Administrator, and issues a TGT for Administrator — with no verification that you're actually Administrator. The CA's signature is all the proof the KDC needs.

ESC8 — Why It Works

The ADCS HTTP enrollment endpoint accepts NTLM authentication. Coerce a DC's machine account to authenticate to you (PetitPotam, PrintSpooler) → relay that auth to the enrollment endpoint → get a certificate for the DC machine account → PKINIT → TGT → DCSync. The relay succeeds because the endpoint doesn't validate whether the relayed authentication should be allowed to enroll. Same "authorization at the service" property from Module 1.

Golden Certificate — The Ultimate Persistence

The CA private key never rotates — ever — unless someone explicitly replaces the entire CA certificate, which is a massive PKI operation most orgs will never perform. A certificate forged with the CA private key will work indefinitely. Exfiltrating the CA private key is treated as a full domain compromise indicator because of this.

⚡ Commands: Domain Persistence → 05

The Practical Reality

ContextWhat You Actually Do
Standard pentestDCSync, save KRBTGT + Administrator hash, done
OSCP examDCSync, grab proof.txt, move to next machine
Red teamAll persistence techniques matter

Why KRBTGT Hash = Full Domain Compromise

KRBTGT hash is the root of all Kerberos trust. Everything else flows from it. DA is a group membership — it can be removed. The KRBTGT hash lets you forge group memberships. Those are not equivalent. You haven't fully compromised a domain until you have the KRBTGT hash.

Most orgs have never rotated KRBTGT in the domain's entire lifetime. Even after a full domain password reset, forged tickets from the old hash work until KRBTGT is reset twice (DCs cache the previous hash for continuity).

Silver Ticket Blind Spot

Silver Tickets are forged AP-REQs — the service decrypts them locally, KDC is never contacted. Zero event logs on the DC. SIEM solutions watching 4768/4769 are completely blind to it. The tradeoff: works on one service only vs Golden Ticket which works everywhere but touches the KDC.

Module 8 — Forest & Trust Attacks

⚡ Commands: Forest & Trusts → 05
SID historytrusts cross-forestAES

Trust Types and Exploitability

Trust TypeSID FilteringExploitability
Parent-Child (same forest)Disabled by defaultAlways exploitable
Tree-Root (same forest)Disabled by defaultAlways exploitable
External (different forest)Enabled by defaultSID history blocked; Kerberoasting still works
Forest trustDepends on configIf SID filtering off → SID history works

Why Parent-Child Is Always Exploitable

SID filtering is never applied on trusts within the same forest. If you own a child domain, you forge an inter-realm TGT with the Enterprise Admins SID (forest_root_SID-519) in the extra-sids field. The forest root's KDC receives it, sees the EA SID in the PAC, and grants forest-wide admin. No way around this without restructuring the forest.

AES vs RC4 on Trust Relationships

If RC4 is allowed on a trust, the trust key is an RC4/NTLM hash — obtainable via DCSync (stored as the [domain]$ account). With the RC4 trust key you can forge trust tickets offline without touching the KDC. AES enforcement raises the bar significantly — the trust key becomes a derived AES key. That's why "enforce AES on domain trusts" is the remediation for that finding.

Module 9 — Defense Evasion & OPSEC

⚡ Commands: Defense Evasion → 05

The Noise Spectrum

Loudest ↑ Mimikatz on disk + executed directly PSExec lateral movement SharpHound default (10k LDAP queries in 30sec) Password spray too fast → lockout WMI/WinRM execution Targeted LDAP queries Kerberoasting (single request) Quietest ↓ Silver Ticket (never touches DC, zero event logs) LDAP reads (looks like normal admin traffic) LOLBins (trusted, signed, expected behavior)

Why AMSI Bypasses Work

AMSI is implemented as amsi.dll loaded into the PowerShell process. Bypasses patch the scanning function in memory to always return "clean." You're not evading the AV engine — you're disabling the pipe that feeds content to it. Specific bypass strings are signatures themselves now; implementations rotate constantly.

ETW — The Deeper Layer

ETW is the real-time telemetry stream feeding most EDR products. It sees Kerberos requests, process creation, network connections, and memory allocations — even if you bypassed AMSI. Modern EDRs that monitor for self-patching behavior will catch ETW patching itself.

Silver Ticket blind spot: 4769 is only logged on the DC. Silver Tickets never touch the DC — the service decrypts them locally. Zero DC event logs. SIEM watching Kerberos event IDs is completely blind to Silver Ticket auth.

The Assumed Breach Mindset

Assume you're being watched from the moment you get a foothold. Clear PowerShell history after sensitive commands. Remove tools from disk after use. Never reuse the same technique repeatedly — pattern recognition is how SIEMs catch you.

Module 10 — Capstone: Full Engagement Flow

The Six Phases

Phase 1 — Initial Foothold DNS recon → DC hostnames, domain name, subnets OSINT → email format, employee names for spray list Password spray → Season+Year, Company+Year, Welcome1! One valid credential → you're in Phase 2 — Enumerate Everything First SharpHound immediately (DCOnly if monitored) Parallel: SYSVOL, open shares, GetUserSPNs, GetNPUsers, findDelegation, certipy find, nltest /domain_trusts BloodHound: shortest path, Kerberoastable, AS-REP, GPO write, DCSync rights, foreign memberships Never exploit before enumeration is complete Phase 3 — Identify the Path BloodHound path exists? → follow it ADCS vulnerable? → ESC8/ESC1 first (fastest DC hash path) Kerberoastable DA? → crack it Unconstrained deleg? → coerce + capture Local admin anywhere? → sweep + check sessions Phase 4 — Execute ACL abuse → shadow creds over password reset Kerberoast → RC4 unless monitored, crack offline ADCS → ESC8: relay→cert→DCSync | ESC1: two certipy commands Lateral → WMI/WinRM, mark owned, requery BloodHound every hop Phase 5 — DA and Beyond DCSync immediately → save KRBTGT + Administrator hash Check trusts → SID history toward forest root ADCS present → extract CA private key → golden certificate Phase 6 — Document Chain the findings. One chain > five standalone findings. Every finding: title, severity, evidence, attack narrative, business impact, remediation.

The Mental Model

AD is a database (LDAP) ↓ Authentication is Kerberos tickets and NTLM hashes ↓ Tickets and hashes are fungible credential material ↓ Misconfigured permissions on database objects = attack paths ↓ BloodHound maps those paths as a graph ↓ Your job is to walk the graph from foothold to KRBTGT ↓ KRBTGT = full domain trust anchor = domain owned

Core Heuristics

01
Protocol Feature vs Vulnerability
Most AD attacks are protocol features being abused, not CVEs. Patches rarely fix them. Shift from "what's vulnerable" to "what's misconfigured or default."
02
Who Encrypts What, With Whose Key?
TGT encrypted with KRBTGT → Golden Ticket. TGS encrypted with SVC hash → Kerberoasting / Silver Ticket. AS-REP encrypted with user hash → AS-REP Roasting. Answer this for any blob and you know the attack.
03
Where Does Authorization Actually Happen?
The gap between where defenders think enforcement is and where it actually is = attack surface. KDC doesn't check → Kerberoast. ADCS doesn't check enrollment rights → ESC8. LDAP allows all users to read → enumeration is free.
04
Enumeration Is Free
Any authenticated domain user can read almost all of AD by default. Exhaust enumeration fully before making noise. The information asymmetry between what a low-priv user can read and what defenders assume they can read is a fundamental AD design problem.
05
Default Until Proven Otherwise
SMB signing off on workstations. LDAP signing not enforced. ADCS HTTP with NTLM. RC4 supported. Pre-auth disabled on legacy accounts. Assume the default is in place unless you have evidence it was hardened.
06
Credentials Are Fungible
Hash → PtH. Hash → Overpass-the-Hash → TGT. TGT → any TGS. Certificate → PKINIT → TGT. TGT → DCSync → all hashes. When you get any credential material, ask what other forms you can convert it to.
07
Domain Compromise = KRBTGT Hash
DA is a group membership. It can be removed. The KRBTGT hash lets you forge group memberships. You haven't fully compromised a domain until you have the KRBTGT hash.
08
If DC Isn't Involved, It Might Not Be Logged
Silver Tickets never touch the DC = zero DC event logs = SIEM blind. The stealthier the attack, the more it bypasses the DC. Route around the DC when stealth matters.

Rabbit Hole Detection

You're in a rabbit hole if: 30+ min on the same path with no new owned nodes, next step requires waiting for an external event, hashes won't crack despite good wordlists, or you're 4+ ACL hops deep with no guarantee the chain is valid.

When this hits: stop, go back to step 1, try a completely different branch.
